## Current State Assessment

### What works
- All 9 Python modules are implemented and structurally sound
- Previous run produced CSV results (latency + occlusion) with 10 objects, 100 reps
- Latency test **passes** both MAR (≤400 ms) and IDE (≤100 ms): P95 ≤ 171 ms
- Intent Precision Δ = +4.4% (passes MAR >0%, **fails** IDE ≥10%)
- Plotting pipeline generates 8 figures + LaTeX table

### Blocking issues
1. **No `.npz` object files on disk** — `objects/parametric/` and `objects/ycb/` are empty. `run.py` will exit immediately with "No objects available."
2. **No `libgrasp_preshaping.so` on disk** — not in `src/grasp_preshaping/lib/` or `target/release/`. The Rust library must be built first.
3. **No `data/finger_contact_lut.npz` on disk** — the LUT is required by the Rust `.so` at initialization (`c_api.rs:334`). Without it the library will panic.
4. **No figure PDFs/PNGs on disk** — only `test1_results_table.tex` exists

### Critical accuracy issue
- **Wrist camera geometry is wrong**: `view_geometry.py:35-43` has the wrist camera at `(0.08, -0.02, 0.0)` looking forward `(1, 0, 0)`. The real 8_cm mount from `camera_mounts.yaml:114-126` is at `(0.01585, -0.091762, 0.160955)` with quaternion `(-0.5, -0.5, 0.5, -0.5)` — which means the camera looks **downward** from ~16 cm above the palm, not forward. This fundamentally changes occlusion patterns.

### Secondary issues
- `matplotlib` and `trimesh` are not in `docker/Dockerfile` (only needed for local run)
- Wrist rotation errors are very high (74°–104° mean), suggesting the SMC sampler struggles with the unrealistic point clouds produced by the wrong camera geometry
- All hand approaches are identical forward approaches — no variation for different grasp types

### Phase 1: Fix Camera Geometry to Match Real Hardware

- [ ] **1.1** Derive the real wrist camera frame from `camera_mounts.yaml` 8_cm mount:
  - Position (screw frame → palm frame): `(0.01585, -0.091762, 0.160955)` — this is already in palm frame
  - Quaternion `(-0.5, -0.5, 0.5, -0.5)` (xyzw convention from YAML) — convert to rotation matrix
  - Compute forward direction: the camera's optical axis in palm frame
  - The quaternion represents a 180° rotation around the `(1, 1, 1)/√3` axis, which maps:
    - Camera Z (optical axis) → palm -X (looking down at the hand from above)
    - Camera X → palm Z
    - Camera Y → palm -Y
  - So the camera looks in the **-X direction** (downward toward the hand), not +X (forward)
  - Rationale: This is the single most impactful fix. The current forward-looking wrist camera produces unrealistic occlusion patterns.

- [ ] **1.2** Update `view_geometry.py` `WRIST_CAMERA_LOCAL`:
  - Set `position` to `np.array([0.01585, -0.091762, 0.160955], dtype=np.float32)`
  - Set `forward` to the computed optical axis direction (approximately `(-1, 0, 0)` after quaternion rotation — but compute it exactly)
  - Set `up` accordingly to form a right-handed frame
  - Keep `fov_h_deg: 58.0`, `fov_v_deg: 45.0` (D435 specs)
  - Adjust `near_m` and `far_m` — the camera is 16cm above the palm, so objects at the hand (~15cm approach distance) are ~30cm away. Set `near_m: 0.10`, `far_m: 0.80`
  - Rationale: Makes the synthetic test representative of the real system.

- [ ] **1.3** Refine `HEAD_CAMERA_LOCAL` for realism:
  - Current: position `(-0.15, 0.0, 0.30)`, forward `(0.75, 0.0, -0.65)` — this is reasonable for glasses-mounted
  - Adjust near/far: `near_m: 0.15` (can't focus closer than ~15cm), `far_m: 2.0`
  - Keep position and forward as-is (already reasonable for head-mounted)
  - Rationale: Minor refinement, less critical than wrist camera.

- [ ] **1.4** Add a geometry validation function to `view_geometry.py`:
  - Add `def validate_camera_frustum(camera_def, test_point=(0, 0, 0))` that checks if the object origin falls within the camera frustum
  - Print diagnostic info: distance to test point, whether it's in frustum, angular offset from center
  - Rationale: Makes it easy to verify the new geometry covers the objects.

## Potential Risks and Mitigations

1. **Rust library won't build locally**
   - Mitigation: Check Rust toolchain (`rustup show`), ensure `cargo build --release --lib` succeeds. The `Cargo.toml` has no ROS dependencies — pure Rust + nalgebra + npyz + serde.

2. **finger_contact_lut.npz doesn't exist**
   - Mitigation: Run `python src/grasp_preshaping/scripts/model.py` to regenerate. This requires the MIA hand URDF/model but should work standalone.

3. **Corrected camera geometry makes some objects invisible**
   - Mitigation: The dry-run mode (Phase 2.3) will catch this before the full run. Adjust approach poses or camera near/far planes as needed.

4. **Intent precision Δ still below 10% after geometry fix**
   - Mitigation: The geometry fix should help significantly (more realistic occlusion = bigger multi-view advantage). If still below, consider adding more challenging objects (high self-occlusion) or increasing repetitions for statistical stability.

5. **Baseline computation times out (120s per object)**
   - Mitigation: The baseline uses 100k prediction samples and 10 SMC iterations. With 10 objects, total baseline time is ~20 minutes. Increase `--baseline-timeout` if needed.

---

## Alternative Approaches

1. **Run inside Docker instead of locally**: If building the Rust library locally is problematic, the existing Docker setup can be used. This avoids toolchain issues but requires Docker/Podman. The `ffi_bridge.py` already searches the Docker install path first.

2. **Use the existing CSV results with restyled figures**: If the camera geometry fix is deferred, the existing results can still be used with improved figures. The latency results are solid; only the intent precision Δ is borderline.

3. **Skip YCB fallbacks, use only 7 parametric objects**: The 7 parametric objects cover all three grasp types (cylindrical, pinch, lateral) and provide sufficient variety. The YCB fallbacks add realism but aren't strictly necessary.

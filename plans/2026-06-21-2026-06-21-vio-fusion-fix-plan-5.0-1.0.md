## Remaining Issues Analysis (Priority Order)

### Issue #1: Jetson Code Not Deployed (CRITICAL BLOCKER)
- **Impact**: 241 rotation_hard rejections at ~110deg (ArUco PnP ambiguity).
  Arm VIO correction yield is 0.2% (1 correction in 462 markers). Arm VIO
  is INVALID for the entire run.
- **Fix**: Rebuild and redeploy Jetson Docker image.

### Issue #2: TF Timestamp Domain Mismatch — "Extrapolation Into Future" (HIGH)
- **Symptom**: 4 TF lookup failures with "Requested time X but latest data is at
  time Y" where X > Y by 0.2-2.1 seconds.
- **Root cause**: The relay stamps corrected TF with the **odom message timestamp**
  (`_resolve_tf_stamp`), but the fusion node looks up TF at the **cloud header
  timestamp**. These are in the same clock domain (chrony OK), but the cloud
  arrives ~0.3-0.8s after the odom (transport + decompression latency). The relay
  rate-limits to 20Hz, so the latest TF stamp may be older than the cloud stamp
  if the relay hasn't published a TF for that timestamp yet.
- **Evidence**: Line 815: Requested 1782053269.007 but latest TF is 1782053268.801
  (0.2s gap). Line 3005: Requested 1782053297.731 but latest is 1782053296.618
  (1.1s gap).
- **Current mitigation**: transform_tolerance_s=1.0s timeout helps but doesn't
  fully solve it — the relay's 20Hz rate means TF stamps are up to 50ms apart,
  but the cloud-to-odom latency gap can be larger.

### Issue #3: Arm VIO Runaway Divergence (CRITICAL — ROOT CAUSE)
- **Symptom**: Arm odom shows 6.9m frame jumps, 231m/s velocity, covariance
  1.68e+02. Head-arm relative distance ranges 0.15-6.45m (should be <1.5m).
- **Root cause**: OpenVINS arm estimator diverges. The 241 rotation_hard
  rejections mean ArUco corrections can't get through (PnP ambiguity produces
  ~110deg rotation errors that exceed the 90deg hard gate). Without corrections,
  VIO drift compounds. The adaptive chi2 gate (Phase 1.4) would help but is
  not deployed.
- **Impact**: 2214 TF jump warnings, arm corrected TF jumping 6.754m repeatedly.

### Issue #4: TF Chain FLIPPED (50% disconnected) (MEDIUM)
- **Symptom**: All 4 TF chain edges (head_imu, arm_imu, head_depth_optical,
  arm_depth_optical) show "FLIPPED" — connected 8 out of 16 diagnostic checks.
- **Root cause**: The relay rate-limits to 20Hz but the diagnostic checks at
  ~2Hz. When the relay's rate limiter skips a cycle AND the corrected TF cache
  expires, the chain breaks for that diagnostic window. The intermittent
  disconnection correlates with the VIO divergence periods.
- **Impact**: Fusion node TF wait gate stays open (it opened after ~40s) but
  individual cloud transforms fail intermittently.

### Issue #5: Dual-View Ratio Only 33.7% (MEDIUM)
- **Symptom**: 32 dual-view, 63 cam1_only out of 86 published clouds.
  Degraded for 6 out of 8 intervals.
- **Root cause**: The arm TF chain is unreliable (Issue #3), so arm cloud
  transforms fail more often than head. When only head transforms, it's
  counted as cam1_only.
- **Impact**: Fused pointclouds are often head-only, defeating the purpose
  of dual-view fusion.

### Issue #6: Relay WAITING for 20s at startup (LOW)
- **Symptom**: Relay shows "head: WAITING (0 msgs), arm: WAITING (0 msgs)"
  for the first 20 seconds.
- **Root cause**: OpenVINS takes ~20s to initialize and start publishing odom.
  This is expected behavior per CURRENT_ISSUES.md Q6.
- **Impact**: Fusion node TF wait gate blocks for ~40s. This is expected.

  the arm config in the running container with the source file.

### Phase 2: Fix TF Timestamp Domain Mismatch (HIGH)

- [ ] 2.1 Add a **latest-available fallback** to the fusion node's TF lookup.
  When `lookup_transform` at the cloud header stamp fails with
  "extrapolation into the future", retry with `rclpy.time.Time()` (latest
  available). This is safe because the corrected TF is already smoothed by
  the relay's LPF — using a slightly newer TF is better than dropping the
  cloud entirely.
  File: `src/pointcloud_fusion/pointcloud_fusion/pointcloud_fusion_node.py`
  Location: `_process_clouds` TF lookup block (~line 549-557)

- [ ] 2.2 Increase the relay's `tf_publish_max_hz` from 20 to 30 to reduce
  the TF stamp gap. 20Hz means up to 50ms between TF stamps; at 30Hz it's
  33ms. This is still well below the 100Hz that caused DDS storms.
  File: `config/prosthesis_config.yaml`

- [ ] 2.3 Add a diagnostic counter for "extrapolation into future" vs other
  TF failure types so we can track whether 2.1 is effective.
  File: `src/pointcloud_fusion/pointcloud_fusion/pointcloud_fusion_node.py`

### Phase 3: Reduce TF Jump Noise from Corrected TF (MEDIUM)

- [ ] 3.1 The corrected TF is jumping 0.681-6.754m because the ArUco-corrected
  frame from the Jetson is itself unstable (arm VIO divergence causes the
  corrected frame to jump when reanchoring fires). The LPF alpha=0.3 smooths
  translation but the **rotation** is passed through unfiltered (line 532:
  `rebroadcast.transform.rotation = tf_corrected.transform.rotation`).
  Apply the same LPF to rotation quaternion components.
  File: `src/camera/camera/openvins_odom_tf_relay.py` (~line 523-532)

- [ ] 3.2 Add a **rotation jump gate** on the corrected TF path. When the
  rotation delta between consecutive corrected TFs exceeds a threshold
  (e.g., 30deg), suppress the broadcast and use the cache instead. This
  prevents the 2214 TF jump warnings that flood the diagnostic output.
  File: `src/camera/camera/openvins_odom_tf_relay.py`

### Phase 4: Improve Fusion Node Resilience (MEDIUM)

- [ ] 4.1 When only one camera's cloud transforms successfully, attempt the
  other camera's transform with `rclpy.time.Time()` (latest available) as
  a fallback before giving up on dual-view. Currently if one fails, the
  entire batch becomes cam1_only.
  File: `src/pointcloud_fusion/pointcloud_fusion/pointcloud_fusion_node.py`

- [ ] 4.2 Add a **TF health metric** to the fusion node's stats line:
  report the TF success rate per camera over the stats interval. This
  makes it visible when one camera's TF chain is degraded.
  File: `src/pointcloud_fusion/pointcloud_fusion/pointcloud_fusion_node.py`

### Phase 5: OpenVINS Arm Stability Investigation (ONGOING)

- [ ] 5.1 After deploying the Jetson changes (Phase 1), monitor whether the
  adaptive chi2 gate allows corrections through during arm VIO divergence.
  The recovery chi2 multiplier (5.0x) should widen the gate from 10.83 to
  ~54, which would have accepted 40% of the currently-rejected corrections.

- [ ] 5.2 If arm VIO still diverges after Phase 1, investigate the OpenVINS
  estimator config for the arm camera. Key suspects:
  - IMU noise/bias parameters (too aggressive integration)
  - Feature tracking quality (insufficient features on arm camera)
  - Initialization quality (arm may initialize poorly)

- [ ] 5.3 Consider adding a **velocity-based VIO health gate** in the relay:
  when arm VIO velocity exceeds 5m/s (clearly diverging), suppress the arm
  TF entirely and rely on the last-good cache. This prevents the 6.754m
  corrected TF jumps from propagating.
  File: `src/camera/camera/openvins_odom_tf_relay.py`

## Potential Risks and Mitigations

1. **IPPE_SQUARE may not eliminate all rotation_hard rejections**
   Mitigation: The iterative fallback with useExtrinsicGuess=True provides
   a secondary path. Monitor rejection types post-deployment.

2. **Latest-available TF fallback may introduce small positional errors**
   Mitigation: The relay's LPF already smooths the corrected TF, so the
   positional error from using a slightly newer TF is bounded by the LPF
   settling time (~3 frames at 20Hz = 150ms).

3. **Rotation LPF may smear fast legitimate rotations**
   Mitigation: Use alpha=0.5 for rotation (faster settling than translation's
   0.3) and add a jump gate that bypasses the LPF for small deltas.

4. **Increasing tf_publish_max_hz may reintroduce DDS congestion**
   Mitigation: 30Hz is still 3x lower than the original 100Hz. Monitor
   DDS retransmission counters in the sysmon overlay.

# V16 Regression Analysis & Fix Plan

## Objective

Fix the v16 regression where `published=0` for the entire run, caused by two interacting issues:
1. The init guard in the relay may be blocking TFs (can't confirm due to `--log-level warn`)
2. The TF wait gate in the fusion node never opens despite TF diagnostics showing "All chains healthy"

## Root Cause Analysis

### Issue 1: Relay Init Guard — Indeterminate

**Status:** Cannot confirm if blocking or passing.

The relay is launched with `--log-level warn` (`pipeline.launch.py:290`), which suppresses ALL info-level logs including:
- `"OpenVINS odometry TF relay active"` (startup confirmation)
- `"head: OpenVINS initialized, publishing TF ..."` (init guard passing)
- `"Relay #N: pose=..."` (periodic odom relay confirmation)

**Evidence that the guard MAY be passing:**
- OpenVINS C++ code at `ROS2Visualizer.cpp:393` already gates publishing: `if (!_app->initialized() || (timestamp - _app->initialized_time()) < 1) return;` — so by the time odom messages reach the relay, the EKF has been running for at least 1 second.
- The covariance is filled from `StateHelper::get_marginal_covariance` which should be non-zero after EKF updates.
- The Jetson log shows bg/ba values that are changing (marker-6) or frozen (marker-7), both indicating the EKF is running.

**Evidence that the guard MAY be blocking:**
- The fusion node never publishes, which could be caused by missing TFs.
- The TF diagnostics shows "All chains healthy" — but this uses `can_transform`, which only checks path existence, not data availability at a specific time.
- OpenVINS also publishes TFs directly on `/tf` over DDS (if `publish_global2imu_tf` is true, which it is by default). The diagnostics could be seeing these DDS TFs, not the relay's.

### Issue 2: TF Wait Gate Never Opens — CONFIRMED ROOT CAUSE

The TF wait gate in `pointcloud_fusion_node.py:751-815` uses `lookup_transform(marker_map, depth_optical_frame, Time(), timeout=1.0)` which always fails.

The TF diagnostics uses `can_transform(marker_map, depth_optical_frame, Time(), timeout=1.0)` which passes from t+32s.

**Why `can_transform` passes but `lookup_transform` fails:**

The OpenVINS `/tf` publisher at `ROS2Visualizer.cpp:454` uses `_node->now()` as the timestamp:
```cpp
trans.header.stamp = _node->now();  // Jetson wall clock
```

The relay at `openvins_odom_tf_relay.py:337` uses the odom message timestamp:
```python
tf_msg = _make_transform(parent, child, x, y, z, qx, qy, qz, qw, msg.header.stamp)
```

The odom message timestamp comes from `ROS2Visualizer.cpp:408`:
```cpp
odomIinM.header.stamp = ROSVisualizerHelper::get_time_from_seconds(timestamp);
```

Where `timestamp` is the OpenVINS internal time (camera hardware clock). This is NOT wall clock time — it's based on the camera's clock domain.

The fusion node's `lookup_transform` uses `rclpy.time.Time()` which resolves to the host's current wall clock time. If the TF data has timestamps from the camera's clock domain (which could be very different from wall clock), the `lookup_transform` will fail because it can't find data at the requested wall-clock time.

`can_transform` only checks if a path exists in the TF graph — it doesn't care about timestamps. This explains why it passes while `lookup_transform` fails.

**Why v15 worked:**
- v15 did NOT have the TF wait gate. The fusion node processed clouds even when TF lookups failed (logging `tf_fail` counts but still publishing).
- v15 did NOT have the relay init guard. The relay published TFs immediately from the first odom message.

## Implementation Plan

### Phase 1: Fix the TF Wait Gate (CRITICAL — unblocks v16)

- [ ] **Task 1.1:** Change `_check_tf_ready` to use `can_transform` instead of `lookup_transform`. The gate only needs to know if the TF path exists, not retrieve actual data. `can_transform` is sufficient for this purpose and doesn't fail on timestamp mismatches.

  File: `src/pointcloud_fusion/pointcloud_fusion/pointcloud_fusion_node.py:768-776`
  Change `self._tf_buffer.lookup_transform(...)` to `self._tf_buffer.can_transform(...)` and adjust the exception handling.

- [ ] **Task 1.2:** Add a debug-level log in `_check_tf_ready` that shows the actual TF lookup error when it fails, so future debugging isn't blind. Currently the `except Exception: continue` swallows all errors silently.

  File: `src/pointcloud_fusion/pointcloud_fusion/pointcloud_fusion_node.py:775-776`

### Phase 2: Fix Relay Observability (HIGH — enables debugging)

- [ ] **Task 2.1:** Change the relay's log level from `warn` to `info` in the launch file, OR change the init guard log message to `warn` level so it's visible even with `--log-level warn`.

  File: `src/prosthesis_launch/launch/pipeline.launch.py:290`
  Option A: Remove `arguments=["--ros-args", "--log-level", "warn"]`
  Option B: Change the init guard log from `self.get_logger().info(...)` to `self.get_logger().warn(...)` in `openvins_odom_tf_relay.py:323-329`

- [ ] **Task 2.2:** Add a counter-based periodic log at WARN level in the relay that reports how many odom messages have been processed and whether each camera is initialized. This ensures visibility even with `--log-level warn`.

  File: `src/camera/camera/openvins_odom_tf_relay.py`

### Phase 3: Relax the Init Guard (MEDIUM — defensive)

- [ ] **Task 3.1:** Add a fallback timeout to the init guard. If no covariance-passing message arrives within 30 seconds, start publishing anyway and log a warning. This prevents the relay from being permanently blocked if OpenVINS never publishes non-zero covariance.

  File: `src/camera/camera/openvins_odom_tf_relay.py:308-329`
  Add a startup timestamp and check: if `now - startup > 30s` and still not initialized, force-initialize with a warning.

- [ ] **Task 3.2:** Lower the covariance threshold or use an alternative check. Instead of `sum(c^2) > 1e-12`, check if the position is non-trivial (not near origin, e.g., `sqrt(x^2+y^2+z^2) > 0.001`). This is a more robust indicator that the EKF has converged.

  File: `src/camera/camera/openvins_odom_tf_relay.py:313-317`

## Verification Criteria

- [ ] The relay logs "OpenVINS initialized" for both cameras within 60 seconds of startup
- [ ] The fusion node logs "TF tree connected" within 60 seconds of startup
- [ ] The fusion node publishes > 0 point clouds within 90 seconds of startup
- [ ] The `published=0` regression is resolved — stats show non-zero publishes
- [ ] If the init guard still blocks, the 30-second fallback kicks in and publishes anyway

## Potential Risks and Mitigations

1. **Risk:** Changing `lookup_transform` to `can_transform` in the TF wait gate might let the fusion node start processing before actual TF data is available, causing TF lookup failures in the main processing loop.
   **Mitigation:** The main processing loop already handles TF lookup failures gracefully (it logs `tf_fail` and skips the frame). The v15 run showed this working fine.

2. **Risk:** The 30-second fallback might publish garbage TFs if OpenVINS hasn't converged.
   **Mitigation:** The fusion node's per-frame TF lookups will fail for garbage TFs, so no corrupted point clouds will be published. The system degrades gracefully to "no output" rather than "wrong output".

3. **Risk:** Changing the relay log level to `info` might produce too much output.
   **Mitigation:** Use counter-based throttled logging (every 100 messages or every 10 seconds) rather than per-message logging.

## Alternative Approaches

1. **Remove the TF wait gate entirely:** Revert to v15 behavior where the fusion node processes clouds even when TF lookups fail. This is the simplest fix and matches the proven v15 behavior. The gate was supposed to reduce warning spam during startup, but it introduced a worse problem.

2. **Use `can_transform` only for the gate, keep `lookup_transform` for actual processing:** This is the recommended approach — the gate checks connectivity, the processing code handles individual lookup failures.

3. **Sync Jetson and host clocks via NTP/PTP:** This would fix the timestamp mismatch that causes `lookup_transform` to fail. But it's a system configuration change, not a code fix, and adds deployment complexity.

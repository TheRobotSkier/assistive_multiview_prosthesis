## Issue 1: Pose vs PoseStamped Type Mismatch (P0)

### Problem

The preshaping bridge publishes `geometry_msgs::msg::Pose` on `/grasp_preshaping/target_hand_pose`:
- `preshaping_service_bridge_node.cpp:177`: `create_publisher<geometry_msgs::msg::Pose>(...)`

The proximity controller subscribes to `geometry_msgs::msg::PoseStamped` on the same topic:
- `grasp_proximity_controller_node.py:90-94`: `create_subscription(PoseStamped, ...)`

ROS 2 does exact type matching — these are incompatible. The proximity controller's `_on_planned_hand_frame` never fires, so `_try_commit_plan` never commits, so no wrist or finger commands are ever sent.

### Fix

Change **both** sides to use `PoseStamped` so the message carries a frame_id and timestamp for downstream consumers.

### Implementation Tasks

- [ ] **Task 1.1**: In `preshaping_service_bridge_node.cpp:177`, change the publisher type from `geometry_msgs::msg::Pose` to `geometry_msgs::msg::PoseStamped`:
  - Change `create_publisher<geometry_msgs::msg::Pose>(...)` to `create_publisher<geometry_msgs::msg::PoseStamped>(...)`
  - `geometry_msgs/msg/pose_stamped.hpp` is already included (line 13)

- [ ] **Task 1.2**: In `preshaping_service_bridge_node.cpp:538-547`, change the published message from `Pose` to `PoseStamped`:
  - Change `geometry_msgs::msg::Pose target_pose;` to `geometry_msgs::msg::PoseStamped target_pose;`
  - Set `target_pose.header.frame_id` to the input pose's frame_id (use `pose.header.frame_id` from the local `pose` variable which is a `PoseStamped` — see line 280, 315)
  - Set `target_pose.header.stamp` to `this->now()`
  - The position and orientation fields move to `target_pose.pose.position` and `target_pose.pose.orientation`

- [ ] **Task 1.3**: In `preshaping_service_bridge_node.cpp:635`, change the member type:
  - `rclcpp::Publisher<geometry_msgs::msg::Pose>::SharedPtr` → `rclcpp::Publisher<geometry_msgs::msg::PoseStamped>::SharedPtr`

- [ ] **Task 1.4**: Verify the proximity controller already subscribes to `PoseStamped` — it does at `grasp_proximity_controller_node.py:90-94`. No change needed on that side.

- [ ] **Task 1.5**: Verify no other subscriber expects `Pose` on this topic. Search for any other consumers of `/grasp_preshaping/target_hand_pose`.

## Issue 2: External Twist Stale Threshold Too Tight (P1)

### Problem

The twist propagation node's external twist max age is 0.5s (`twist_propagation_node.py:501`), but the `/hand_twist` relay publishes at ~1-2 Hz. At the 50 Hz cycle rate, the twist is "stale" for ~490ms out of every 500ms window, causing constant fallback to finite-difference estimation and INFO-level stale warnings that flood the log at 50 Hz.

### Fix

Increase the default threshold to 2.0s (comfortably above the relay's publish interval) and throttle the stale log message.

### Implementation Tasks

- [ ] **Task 2.1**: In `twist_propagation_node.py:501`, change the default parameter value:
  - `self.declare_parameter("external_twist_max_age_s", 0.5)` → `self.declare_parameter("external_twist_max_age_s", 2.0)`

- [ ] **Task 2.2**: In `config/prosthesis_config.yaml:266`, change the value:
  - `external_twist_max_age_s: 0.5` → `external_twist_max_age_s: 2.0`

- [ ] **Task 2.3**: In `config/prosthesis_config.yaml:496`, change the value:
  - `external_twist_max_age_s: 0.5` → `external_twist_max_age_s: 2.0`

- [ ] **Task 2.4**: In `twist_propagation_node.py:906-908`, throttle the stale warning to avoid log spam at 50 Hz:
  - Add `throttle_duration_sec=5.0` to the `self.get_logger().info(...)` call so it only prints once every 5 seconds instead of every 20ms cycle

## Issue 4: Wrist Driver No Retry on Failed Position Commands (P1)

### Problem

The wrist driver's `_on_position_cmd` (`wrist_driver_node.py:106-125`) makes a single attempt to write the goal position to the Dynamixel servo. When communication fails (common — see errors every 5-20s in the log), the command is silently dropped. The servo stays at its previous position.

### Fix

Add up to 2 retries with a short delay (10ms) when the initial write fails. Also retry the acceleration write.

### Implementation Tasks

- [ ] **Task 4.1**: In `wrist_driver_node.py`, add a new parameter for retry count:
  - In `__init__`, add: `self.declare_parameter('write_retries', 2)` 
  - Store: `self._write_retries = self.get_parameter('write_retries').value`

- [ ] **Task 4.2**: In `wrist_driver_node.py`, add `import time` at the top of the file (it's not currently imported).

- [ ] **Task 4.3**: In `wrist_driver_node.py:106-125`, refactor `_on_position_cmd` to retry the position write on failure:
  - Extract the `write4ByteTxRx` call into a loop with `self._write_retries` attempts
  - On each failure, sleep 10ms (`time.sleep(0.01)`) and retry
  - Log a warning only on the final failure (not on intermediate retries)
  - Same retry logic for the acceleration write if `accel > 0`
  - Keep the existing `except (IndexError, OSError)` handler wrapping the whole thing

  Pseudocode for the new `_on_position_cmd`:
  ```
  def _on_position_cmd(self, msg):
      if len(msg.data) < 1: return
      target_deg = msg.data[0]
      accel = msg.data[1] if len(msg.data) > 1 else 0.0
      try:
          dxl_pos = _deg_to_dx(target_deg)
          self._write_with_retry(ADDR_GOAL_POSITION, dxl_pos, 'set position')
          if accel > 0:
              self._write_with_retry(ADDR_PROFILE_ACCELERATION, int(accel), 'set acceleration')
      except (IndexError, OSError) as exc:
          self.get_logger().warn(f'Dynamixel write failed (communication error): {exc}')
  ```

- [ ] **Task 4.4**: Add a `_write_with_retry` helper method to `WristDriverNode`:
  ```
  def _write_with_retry(self, address, value, label):
      for attempt in range(self._write_retries + 1):
          dxl_comm_result, dxl_error = self._packet_handler.write4ByteTxRx(
              self._port_handler, self._motor_id, address, value)
          if dxl_comm_result == COMM_SUCCESS:
              return
          if attempt < self._write_retries:
              time.sleep(0.01)
          else:
              self.get_logger().warn(
                  f'Failed to {label} after {self._write_retries + 1} attempts: '
                  f'{self._packet_handler.getTxRxResult(dxl_comm_result)}')
  ```

- [ ] **Task 4.5**: Also add retry logic to `_publish_state` for the read operations:
  - Wrap each `read4ByteTxRx` in a similar retry loop (1 retry, 5ms delay)
  - This reduces the frequency of dropped state publications

## Issue 5: Twist Propagation Duplicate Preshaping Call (P0)

### Problem

The twist propagation node enters `WAITING_FOR_SEGMENTATION` after publishing a click (line 1767). When the segmented cloud arrives, it transitions to `WAITING_FOR_PRESHAPING` and calls `_schedule_preshaping_call()` (line 1496). This independently calls `/grasp_preshaping/compute_grasp`.

But the pipeline manager also calls the same service via `_request_preshaping()` (`pipeline_manager_node.py:639`) when it receives the object cloud. This results in **two concurrent preshaping calls** — the second one fails with "No points in ROI".

The pipeline manager's own comment at `pipeline_manager_node.py:641-648` says:
> "pipeline_manager is the single owner of preshaping orchestration per segmentation target. twist_propagation should NOT independently call /grasp_preshaping/compute_grasp"

### Fix

Remove the preshaping service call from twist propagation. The node should publish the click and stop — the pipeline manager handles everything downstream (segmentation trigger → preshaping → approach).

### Implementation Tasks

- [ ] **Task 5.1**: In `twist_propagation_node.py`, remove the `_compute_client` creation:
  - Remove lines 745-749 (the `self._compute_client = self.create_client(...)` block)
  - Remove the parameter declaration at line 508 (`self.declare_parameter("compute_grasp_service", ...)`)

- [ ] **Task 5.2**: In `twist_propagation_node.py`, remove the `WAITING_FOR_PRESHAPING` branch in `_cycle_callback`:
  - Remove lines 1481-1484 (the `elif state == CycleState.WAITING_FOR_PRESHAPING:` block)

- [ ] **Task 5.3**: In `twist_propagation_node.py`, change the `WAITING_FOR_SEGMENTATION` branch to NOT call preshaping:
  - When `self._seg_cloud_stamp > self._seg_cloud_stamp_at_trigger` (new cloud arrived), transition directly back to `CycleState.IDLE` instead of `CycleState.WAITING_FOR_PRESHAPING`
  - Remove the `should_call_preshaping = True` assignment
  - Log "Segmented cloud received" but do NOT log "calling preshaping service"

- [ ] **Task 5.4**: In `twist_propagation_node.py`, remove the `_schedule_preshaping_call`, `_on_preshaping_delay_expired`, `_call_preshaping_service`, and `_on_preshaping_response` methods (lines 1793-1847).

- [ ] **Task 5.5**: In `twist_propagation_node.py`, remove the `should_call_preshaping` variable and the post-lock service call block at lines 1494-1496.

- [ ] **Task 5.6**: Remove `compute_grasp_service` from `config/prosthesis_config.yaml` in both sections (lines 269 and 499) — it's no longer needed by the twist propagation node.

## Potential Risks and Mitigations

1. **PoseStamped header frame_id mismatch**: The proximity controller computes distance using only `position` fields — the frame_id in the header is informational. Both poses (current hand and target) should be in the same frame (`marker_map`). Verify that the input pose's frame_id is `marker_map` (it is — confirmed by the log showing `target_frame=marker_map`).
   Mitigation: The distance computation in `_euclidean_distance` only uses position fields, so frame consistency is what matters, not the header.

2. **Increased external_twist_max_age (2.0s) may use stale twist data**: If the arm stops moving and the relay stops publishing, the node could use 2-second-old twist for up to 2 seconds.
   Mitigation: 2 seconds is still short enough that the hand won't have moved significantly. The twist propagation hit detection also checks the actual point cloud, so stale twist would just result in no hit (safe).

3. **Wrist driver retry adds latency**: Each retry adds 10ms. With 2 retries worst case, that's 20ms added to the position command path.
   Mitigation: 20ms is negligible for a wrist servo running at 20 Hz state publish rate. The retry only fires on failure, which is the exception not the norm.

4. **Removing preshaping call from twist propagation**: If the pipeline manager fails to call preshaping for any reason, the grasp won't be planned.
   Mitigation: The pipeline manager is the designed orchestrator. The twist propagation node was making a redundant call that sometimes failed and sometimes conflicted. Removing it simplifies the flow and matches the documented architecture.

## Alternative Approaches

1. **Issue 1 alternative**: Change the proximity controller to subscribe to `Pose` instead of `PoseStamped`. This is simpler (1 line change in Python vs 3 changes in C++), but `PoseStamped` is better practice — it carries frame context.
   Decision: Use `PoseStamped` on both sides for consistency and future-proofing.

2. **Issue 5 alternative**: Add a parameter to disable the twist propagation's preshaping call instead of removing the code. This preserves backward compatibility for mock/sim environments.
   Decision: Remove the code entirely. The pipeline manager owns this responsibility in all environments. Dead code is worse than a clean removal.

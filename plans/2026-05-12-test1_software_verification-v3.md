## 3. File-by-File Implementation Specification

### 3.1 `ffi_bridge.py` — ctypes wrapper

This is the core bridge. It must define Python `ctypes.Structure` classes matching the FFI types from `ffi_types.hpp:20-97` and `c_api.rs:26-109`:

```
Classes to define:
  GraspPoseFFI        — 7 doubles (px,py,pz,qx,qy,qz,qw)
  GraspTwistFFI       — 6 doubles (lx,ly,lz,ax,ay,az)
  PointCloudViewFFI   — 6 size_t + 1 pointer + 1 size_t
  CameraPositionFFI   — 3 floats (x,y,z)
  GraspComputeRequestFFI  — pose + twist + cloud + cameras[4] + n_cameras
  GraspComputeResponseFFI — 26 fields matching the C++ struct

Functions to expose:
  load_library(so_path) → returns CDLL with function signatures configured
  compute(lib, request) → returns (status_code, response, message_string)
  make_request(pose, twist, cloud_np, cameras) → GraspComputeRequestFFI
  response_to_dict(response) → dict with all fields named
```

Key details:
- `PointCloudViewFFI.data_ptr` must be a `ctypes.POINTER(ctypes.c_uint8)` pointing to the numpy array's data buffer. Use `numpy_array.ctypes.data_as(ctypes.POINTER(ctypes.c_uint8))`.
- The `cameras` field is `CameraPositionFFI * 4` (fixed array of 4).
- `n_cameras` is `ctypes.c_uint32`.
- The message buffer is a `ctypes.create_string_buffer(512)`.

### 3.2 `view_geometry.py` — camera positions and frustums

Define the two camera viewpoints used in the real system:

```python
# Head-mounted camera (on glasses, ~40cm above hand, looking forward)

    "fov_v_deg": 45,                    # D435 vertical FOV
    "near_m": 0.1,
    "far_m": 1.0,
}

# Wrist-mounted camera (on prosthesis, ~8cm from hand center)

    "position": [0.08, -0.02, 0.0],    # relative to hand
    "orientation": [0, 0, 0, 1],
    "fov_h_deg": 58,

    "near_m": 0.1,
```

Provide a function `get_camera_world_positions(hand_pose)` that transforms these into world frame given a hand pose.

### 3.3 `occlusion.py` — frustum culling and depth-buffer simulation

Two functions:

```
frustum_cull(points, camera_position, camera_orientation, fov_h, fov_v, near, far)
    → visible_points (N', 3)

depth_buffer_occlude(points, camera_position, camera_orientation, fov_h, fov_v, resolution=640x480)
    → visible_points (N', 3)
```

- `frustum_cull` keeps points inside the viewing frustum (6-plane test).
- `depth_buffer_occlude` additionally removes self-occluded points using a z-buffer:
  1. Project all points into a 2D grid (640x480)
  2. For each pixel, keep only the nearest point
  3. Return the surviving points

For YCB mesh objects, `trimesh` can do proper ray-based visibility, but the z-buffer approach works for all object types and is simpler.

### 3.4 `hand_approaches.py` — per-object hand pose and twist

For each object, define a canonical approach:

```python
APPROACHES = {
    "cylinder_upright": {
        "pose": {"px": -0.15, "py": 0.0, "pz": 0.12, "qx": 0, "qy": 0.707, "qz": 0, "qw": 0.707},
        "twist": {"lx": 0.10, "ly": 0.0, "lz": 0.0, "ax": 0, "ay": 0, "az": 0},
    },
    ...
}
```

The hand is positioned ~15cm away from the object center, oriented toward it, with a small forward velocity. Each approach must be tuned so the SMC sampler's ROI prediction covers the object.

**How to tune**: Run each object once with debug visualization enabled, inspect the debug dump with `visualize_grasp_debug.py`, and verify the ROI bounding box covers the object. Adjust the approach position/direction until it does.

### 3.6 `generate_objects.py` — one-time setup script

Run once before the test. Does two things:

**Parametric objects** (pure numpy):
- `cylinder_upright`: Sample points on cylinder surface (r=0.03, h=0.12), centered at origin
- `cylinder_tilted`: Same, rotated 30° around Y axis
- `ellipsoid`: Sample on ellipsoid (a=0.05, b=0.03, c=0.03)
- `tapered_bottle`: Frustum shape (r_bottom=0.035, r_top=0.025, h=0.18)
- `l_block`: Union of two boxes (6×3×3 cm + 3×3×6 cm), L-shaped
- `small_cube`: Box (2.5×2.5×2.5 cm)
- `thin_plate`: Box (8.5×5.4×0.1 cm)

Each generates ~10,000 surface points, saved as `.npz`.

**YCB objects** (requires mesh files):
- Load `.obj` with `trimesh.load()`
- Sample 10,000 surface points with `mesh.sample(10000)`
- Save as `.npz`

### 3.7 `run.py` — main test orchestrator

```
Usage:
    python run.py                    # Run all Tier A tests + generate figures
    python run.py --tier-a-only      # Only Tier A (planner latency + occlusion)
    python run.py --tier-b           # Also run Tier B (full ROS pipeline)
    python run.py --generate-objects # Run object generation only
    python run.py --figures-only     # Regenerate figures from existing CSVs
```

**Execution flow for `--tier-a-only`** (default):

1. Load the `.so` via `ffi_bridge.py`
2. Load all 10 objects via `object_registry.py`
3. **Latency Test (Tier A)**:
   - For each object:
     - Generate multi-view point cloud (merge both camera frustums via `occlusion.py`)
     - Call `grasp_preshaping_compute()` 10 times
     - Record all response fields to `results/latency_tier_a.csv`
   - Repeat with single-view point cloud (head camera only)
4. **Occlusion Proxy Test**:
   - Set `GRASP_CONFIG_PATH` to baseline config
   - For each object:
     - Run with complete unoccluded cloud → baseline result
   - Set `GRASP_CONFIG_PATH` to production config
   - For each object:
     - Run with single-view cloud → single-view result
     - Run with multi-view cloud → multi-view result
   - Compute Intent Precision Δ
   - Save all results to `results/occlusion_results.csv`
5. Call `plot_results.py` to generate all figures

**Important note on config switching**: The Rust `.so` reads the config once on first call (via `OnceLock`). To switch configs between baseline and production runs, you need to **reload the `.so`** (unload and `ctypes.CDLL()` again) or run the baseline in a separate process. The simplest approach: run the baseline as a subprocess that sets `GRASP_CONFIG_PATH` before importing the `.so`.

## 5. Intent Precision Δ — Exact Metric Definition

For each object, compare single-view and multi-view results against the baseline:

```python
def is_correct_prediction(result, baseline, pose_tol_deg=15.0, pos_tol_mm=10.0):
    """Returns True if the predicted grasp matches the baseline."""
    # 1. Grasp type must match
    if result["grasp_type"] != baseline["grasp_type"]:
        return False

    # 2. Wrist orientation error within tolerance
    wrist_err = quaternion_angular_distance(
        result["wrist_quat"], baseline["wrist_quat"]
    )
    if wrist_err > pose_tol_deg:
        return False

    # 3. Target position error within tolerance
    pos_err = np.linalg.norm(
        np.array([result["target_px"], result["target_py"], result["target_pz"]])
        - np.array([baseline["target_px"], baseline["target_py"], baseline["target_pz"]])
    ) * 1000  # convert m to mm
    if pos_err > pos_tol_mm:
        return False

    return True

# Compute per-condition accuracy
single_view_accuracy = sum(is_correct_prediction(sv, bl) for sv, bl in zip(single_view_results, baselines)) / N * 100
multi_view_accuracy = sum(is_correct_prediction(mv, bl) for mv, bl in zip(multi_view_results, baselines)) / N * 100
delta = multi_view_accuracy - single_view_accuracy
```

**Pass criteria**: Δ > 0% (MAR), Δ ≥ 10% (IDE).

## 8. Risk Mitigation

1. **Config reload issue**: The Rust `.so` uses `OnceLock` for config, meaning it reads the YAML once and caches it forever. To run baseline with different config, use a subprocess that sets `GRASP_CONFIG_PATH` before loading the `.so`. The `run.py` script should handle this automatically.

2. **YCB download unavailable**: The `generate_objects.py` script must include fallback parametric approximations for banana, mug, and drill. These won't be as realistic but will still produce meaningful occlusion.

3. **Hand approach tuning**: This is the most manual step. Budget time for iterative tuning. The debug visualization mode (`debug_visualization: true`) is essential here — run the planner once, inspect the dump, adjust the approach pose.

4. **Stochastic SMC results**: The planner uses random sampling. For the occlusion test, run each condition 10 times and take the best result (highest combined_score) for comparison. This reduces noise from unlucky random seeds.

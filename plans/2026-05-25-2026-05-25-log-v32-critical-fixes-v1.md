# Log v32 Critical Fixes — STOP_ALL Removal, Near Zone Signal, Cylindrical Override

## Objective

Fix three critical issues preventing the system from progressing past APPROACHING:

1. **STOP_ALL wrist conflict**: The EMG state machine publishes `STOP_ALL` on every REST frame, causing the pipeline manager to fight the proximity controller's wrist commands. Remove this entirely — the design intent is that OPEN releases the hand and returns to IDLE, not that REST issues safety stops.

2. **Missing near zone signal**: The proximity controller detects the near zone but never publishes `/proximity/near_zone_entered`, so the pipeline manager can never transition APPROACHING → GRASPING.

3. **Hardcoded cylindrical grasp with 10% initial closure**: Override the preshaping planner's grasp type to always use cylindrical (all three fingers close equally) with a fixed 10% initial closure, letting the force controller handle the rest once near zone is entered.

## Verification Findings

### Why OPEN didn't stop the wrist oscillation

The pipeline manager correctly transitions to RELEASING on OPEN held ≥1.0s (`pipeline_manager_node.py:390-401`). The log confirms this at line 767: `State: APPROACHING -> RELEASING (EMG: OPEN)`. However, **before the OPEN hold completes**, the EMG state machine (running independently at 20 Hz in `NOT_GRASPING` mode) publishes `STOP_ALL` on every REST frame. The pipeline manager's `_on_emg_grasp_intent` handler (`pipeline_manager_node.py:575-579`) converts each `STOP_ALL` into a wrist command `[10.6, 0.0]` (initial hardware position). This fights the proximity controller's `[4.5, 180.0]` at 10 Hz. The wrist oscillates between these two positions.

Even after the OPEN hold completes and the pipeline transitions to RELEASING, the EMG state machine continues publishing `STOP_ALL` (it's in `NOT_GRASPING` mode and REST → `STOP_ALL` is unconditional). So the wrist hold commands continue during RELEASING and IDLE too.

### Force controller only supports cylindrical

The force controller (`force_controller_node.py`) controls all 3 fingers (thumb, index, mrl) with the same PI loop. It has no grasp-type-specific logic. It always applies cylindrical-style control. This confirms the user's intuition — the system should always use cylindrical grasp for now.

## Implementation Plan

### Fix 1: Remove STOP_ALL Wrist Commands from Pipeline Manager

**File**: `src/pipeline_manager/pipeline_manager/pipeline_manager_node.py`

- [ ] **Task 1.1**: Remove the `_on_emg_grasp_intent` callback's wrist command publishing (lines 575-579). The entire `if intent_type == _INTENT_STOP_ALL:` block currently publishes `[self._ensure_wrist_target(), 0.0]` to `/wrist/set_position`. This is the sole cause of the wrist oscillation — it fights the proximity controller during APPROACHING and sends unnecessary hold commands during IDLE.

  **Rationale**: The design intent is that OPEN (held ≥1s) triggers RELEASING → IDLE, which opens the hand and resets everything. REST should be a no-op. There is no scenario where a STOP_ALL wrist command is needed — the proximity controller manages the wrist during APPROACHING, and the pipeline manager manages it during VOLITIONAL. In IDLE/TWISTING/SEGMENTING/PLANNING, no wrist commands should be sent at all.

- [ ] **Task 1.2**: Optionally remove the `_on_emg_grasp_intent` subscription entirely if no other intent types are handled. Currently only `STOP_ALL` is processed. The subscription to `/emg_grasp/intent` and the `_INTENT_STOP_ALL` constant can be removed. The EMG state machine's `RESET_HAND` intent (published on OPEN confirmed) is already ignored.

  **Rationale**: Dead code removal. If intents are needed later (e.g., for VOLITIONAL wrist control), they can be re-added with proper state gating.

### Fix 2: Add Near Zone Publisher to Proximity Controller

**File**: `src/grasp_preshaping/nodes/grasp_proximity_controller_node.py`

- [ ] **Task 2.1**: Add a `Bool` publisher on `/proximity/near_zone_entered` to the proximity controller's `__init__` (after the existing publishers, around line 122). Import `Bool` from `std_msgs.msg` (it's not currently imported).

  **Rationale**: The pipeline manager subscribes to `/proximity/near_zone_entered` (`pipeline_manager_node.py:226`) and transitions APPROACHING → GRASPING on `Bool(True)`. But the proximity controller never publishes this signal. Without it, the system can never reach GRASPING.

- [ ] **Task 2.2**: Publish `Bool(True)` when entering the near zone (line 209, after the log message). Publish `Bool(False)` when leaving the near zone (line 202, after the log message).

  **Rationale**: The pipeline manager only acts on `True`, but publishing `False` on exit is good practice for any future consumer that might track the near zone state.

### Fix 3: Hardcode Cylindrical Grasp with 10% Initial Closure

**File**: `src/grasp_preshaping/nodes/preshaping_service_bridge_node.cpp`

- [ ] **Task 3.1**: After the planner result is logged (around line 514), override the grasp type and closures to always use cylindrical. Replace the computed per-finger closures with hardcoded values:
  - `full_thumb = 0.10` (10% closure)
  - `full_index = 0.10`
  - `full_mrl = 0.10`
  - `ffi_response.grasp_type = kGraspTypeCylindrical` (value 1)
  - Log the override: "Overriding to cylindrical grasp with 10% initial closure"

  **Rationale**: The force controller only supports cylindrical grasp (all 3 fingers). The preshaping planner may return pinch/lateral with zero closure for sparse point clouds. By hardcoding cylindrical with 10% closure, the proximity controller always gets a valid plan with non-zero closures. The 10% gives the hand a visible preshape. The force controller takes over from there once GRASPING is entered.

- [ ] **Task 3.2**: The `preshape_thumb/index/mrl` values (lines 522-524) will automatically be `max(0.10 * 0.3, 0.1) = 0.1` due to `min_closure_amount_` floor. This is fine — the immediate preshape is 10% closure, which is the desired behavior.

  **Rationale**: No additional change needed — the existing `min_closure_amount_` (0.1) ensures at least 10% closure is sent.

- [ ] **Task 3.3**: Rebuild the `grasp_preshaping` package inside the container after the C++ changes. Command: `podman exec prosthesis bash -c 'source /opt/ros/jazzy/setup.bash && cd /prosthesis_ws && colcon build --packages-select grasp_preshaping --cmake-args -DCMAKE_BUILD_TYPE=Release 2>&1'`

  **Rationale**: The preshaping bridge is a C++ node — changes require recompilation.

## Verification Criteria

- [ ] No wrist oscillation during APPROACHING — the proximity controller is the sole publisher to `/wrist/set_position` during APPROACHING
- [ ] APPROACHING → GRASPING transition fires when the hand enters the near zone (distance < 0.08m)

## Potential Risks and Mitigations

1. **Removing STOP_ALL may leave wrist in last position during IDLE**
   Mitigation: This is acceptable — the wrist stays where the proximity controller last set it. If the user wants to reset, they use OPEN which transitions to RELEASING → IDLE. The wrist position is not reset on RELEASING currently, but this can be added later if needed.

2. **Hardcoded 10% closure may be too little/too much for some objects**
   Mitigation: 10% is a conservative preshape that gives a visible hand shape without risking premature contact. The force controller handles the actual grasping force. This can be tuned via the `min_closure_amount` parameter later.

3. **Near zone may trigger too early/late**
   Mitigation: The thresholds are configurable via `proximity_enter_threshold_m` (0.08m) and `proximity_exit_threshold_m` (0.10m). These can be tuned based on physical testing.

## Alternative Approaches

1. **Instead of removing STOP_ALL entirely, gate it by pipeline state**: Only publish wrist hold in IDLE and VOLITIONAL. This preserves the safety-stop behavior for those states. However, the user explicitly stated that STOP_ALL is not part of the design — OPEN is the release mechanism. So full removal is cleaner.

2. **Instead of hardcoding cylindrical in the bridge, override in the proximity controller**: The proximity controller could ignore the planned closures and always use [0.1, 0.1, 0.1]. However, this means the bridge still publishes the wrong values on the planner topics, which could confuse debugging. Overriding at the source (bridge) is cleaner.

3. **Make the grasp type override configurable via parameter**: Add a `force_grasp_type` parameter (default 0 = use planner result, 1 = cylindrical, etc.). This adds flexibility but the user explicitly asked for a hardcoded cylindrical override, so a parameter is unnecessary complexity for now.

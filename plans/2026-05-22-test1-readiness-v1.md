# Test 1: Software Verification — Readiness Plan

## Objective

Prepare the Test 1 (Software Verification) suite for a clean, reproducible run that produces publication-quality figures and valid results. The test validates Req 1.6 (autonomous grasp computation), Req 2.4 (pipeline latency ≤ 400 ms MAR / ≤ 100 ms IDE), and Req 2.7 (intent precision Δ > 0% MAR / ≥ 10% IDE).

---

## Current State Assessment

### What exists and works:
- **All 9 Python modules** are implemented: `run.py`, `run_tier_b.py`, `ffi_bridge.py`, `occlusion.py`, `view_geometry.py`, `hand_approaches.py`, `object_registry.py`, `generate_objects.py`, `plot_results.py`
- **Previous run completed** — CSV results exist in `results/` with 1000 latency rows (10 objects × 100 reps) and 2000 occlusion rows
- **8 figures** are generated by `plot_results.py` (fig1–fig8) plus a LaTeX table fragment
- **Latency results PASS** — all objects well under 400 ms MAR (mean 74–142 ms, P95 ≤ 171 ms)
- **Intent Precision Δ = +4.4% mean** — passes MAR (>0%) but **FAILS IDE (≥10%)**
- **Config files** are properly set up with production and baseline variants

### Critical issues identified:

#### Issue 1: Synthetic camera geometry diverges from the real hardware
The `view_geometry.py` camera definitions are **rough approximations** that do not match the actual D435i mount geometry from `camera_mounts.yaml`:

| Parameter | `view_geometry.py` (synthetic) | Real system (`camera_mounts.yaml`, 8_cm mount) |
|---|---|---|
| Wrist camera position | `(0.08, -0.02, 0.0)` relative to hand | Screw-to-palm transform: `(0.01585, -0.091762, 0.160955)` with quaternion `(-0.5, -0.5, 0.5, -0.5)` — the camera looks **downward**, not forward |
| Head camera position | `(-0.15, 0.0, 0.30)` relative to hand | On forehead — position depends on user head pose, not hand frame |
| Camera orientation | Forward along X-axis | Wrist cam: rotated 90° (looks down at hand); quaternion `(-0.5, -0.5, 0.5, -0.5)` maps palm-X to screw-Z |
| FOV | 58° × 45° | Correct for D435 at 640×480 |

The wrist camera's real orientation is critical: it looks **downward** toward the hand from ~16 cm above, not forward. This fundamentally changes what the camera can see and what is occluded. The synthetic test's forward-looking wrist camera would see a very different portion of the object than the real downward-looking camera.

#### Issue 2: Wrist orientation errors are extremely high
The existing results show mean wrist rotation errors of **74°–104°** across all objects — essentially random wrist orientation. This suggests either:
- The SMC sampler is not converging on wrist pose with only partial point clouds
- The baseline comparison is unfair (different convergence behavior with full vs. partial clouds)
- The hand approach poses may not properly orient the sampling ROI

#### Issue 3: Intent Precision Δ fails IDE threshold
Mean Δ = +4.4% vs. the IDE target of ≥10%. Only `power_drill` achieves a meaningful Δ (+19%). Several objects show negative Δ (cylinder_upright: -2%, tapered_bottle: -3%). This could be a genuine result, but it may also indicate the synthetic setup isn't representative enough to show the multi-view advantage.

#### Issue 4: Figure styling doesn't match project colors
The existing figures use default matplotlib colors (`#4c72b0`, `#55a868`, etc.) rather than the project's established palette (`#5099e9`, `#fffdf6`, `#f4fbf9`). Figures need restyling for consistency with the rest of the report.

## Implementation Plan

### Phase 1: Fix Synthetic Camera Geometry to Match Real Hardware

- [ ] **1.1** Derive the real wrist camera position and orientation from `camera_mounts.yaml`
  - The 8_cm mount has `screw_to_palm` translation `(0.01585, -0.091762, 0.160955)` with quaternion `(-0.5, -0.5, 0.5, -0.5)`. Inverting this gives palm-to-screw, then compose with `screw_to_link` to get the camera position relative to the palm frame.
  - The camera looks **downward** (palm X → screw -Z), so the forward vector in palm frame is approximately `(0, 0, -1)` (down), not `(1, 0, 0)` (forward).
  - Rationale: The test description says "simulated viewpoints representing the head-mounted and prosthesis-mounted camera positions" — these must match the real geometry for the occlusion proxy test to be meaningful.

- [ ] **1.2** Update `WRIST_CAMERA_LOCAL` in `view_geometry.py`
  - Compute the actual camera position relative to the hand center using the 8_cm mount transform chain: `palm_frame → screw_frame → link_frame`
  - Set forward direction to look downward (toward the hand/object), matching the real mount's quaternion rotation
  - Keep FOV at 58°×45° (correct for D435)
  - Adjust near/far planes based on real distances: the camera is ~16 cm above the hand, so near=0.05 m and far=0.5 m is more realistic

- [ ] **1.3** Update `HEAD_CAMERA_LOCAL` in `view_geometry.py`
  - The head camera is on glasses/forehead, approximately 30–40 cm above and slightly behind the hand
  - Position: approximately `(-0.10, 0.0, 0.35)` relative to hand (behind and above)
  - Forward: angled downward ~40° from horizontal, approximately `(0.75, 0.0, -0.65)` — this is already reasonable
  - The key improvement: ensure the near/far planes match (near=0.15 m, far=1.0 m for a head-mounted camera looking at the hand)

- [ ] **1.4** Add a validation script or function that prints the derived camera transforms
  - Print the computed world-frame camera positions and forward vectors for a sample hand pose
  - Compare against the known real system values from `camera_mounts.yaml`
  - This serves as a sanity check before running the full test

## Potential Risks and Mitigations

1. **Camera geometry derivation is complex**
   The 8_cm mount uses quaternion `(-0.5, -0.5, 0.5, -0.5)` which is a 180° rotation. The transform chain (screw→palm inverted, then screw→link) must be computed correctly.
   **Mitigation**: Use the existing `_invert_transform()` function from `publish_camera_mounts.py` as reference. Validate by printing the resulting world-frame camera positions and comparing against known values.

2. **Updated camera geometry may worsen results**
   If the real camera geometry produces more aggressive occlusion, the SMC sampler may fail more often, reducing success rates.
   **Mitigation**: This is actually desirable — it means the test is more representative. If success rates drop too low, the test still provides valid data about the system's limitations.

3. **IDE threshold (Δ ≥ 10%) may still fail**
   The current mean Δ is +4.4%. Even with better camera geometry, it may not reach 10%. This could be a genuine result.
   **Mitigation**: Document honestly. The test description says "MAR > 0%, IDE ≥ 10%" — passing MAR is the minimum acceptable result. The IDE threshold represents an aspirational target.

4. **YCB mesh files may not be available**
   The `objects/ycb/` directory has `.obj` files but they may not be properly formatted.
   **Mitigation**: The `generate_objects.py` script has fallback parametric generators (`--fallbacks` flag). These produce reasonable approximations.

5. **Docker environment may lack matplotlib/trimesh**
   The Dockerfile only installs `dynamixel-sdk` and `requests` via pip.
   **Mitigation**: Add `matplotlib` and `trimesh` to the Dockerfile, or install them at test time with `pip install matplotlib trimesh`.

---

## Alternative Approaches

1. **Keep existing camera geometry, document as "simplified"**: If the camera geometry derivation proves too complex, keep the current approximation but clearly document in the report that the synthetic cameras use simplified frustums. This is less rigorous but avoids the risk of introducing errors.

2. **Use the real TF chain to compute camera positions**: Instead of hardcoding camera parameters, load `camera_mounts.yaml` directly in `view_geometry.py` and compute the transforms dynamically. This ensures the test always matches the current mount configuration. Trade-off: adds a YAML dependency and complexity to the test module.

3. **Run the test with multiple mount configurations**: Instead of just the 8_cm mount, test with 5_cm, 8_cm, 10_cm, and 12_cm mounts to show how camera placement affects multi-view advantage. This would make for a more compelling figure but significantly increases test runtime.

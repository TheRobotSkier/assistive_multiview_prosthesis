# Fix: Interactive Sim Point Cloud Includes Hand Geometry

## Objective

The interactive simulation's point cloud segmentation (`/segmented_object_cloud`) includes parts of the hand in addition to the target object. The root cause is that the ray-cast filtering in `filter_points_by_target_geom` uses a point's 3D position to construct a ray from the camera, but this ray is then re-cast from the camera origin through `mj_ray`, which can hit a **different geometry** than the one that originally generated the depth pixel — specifically, hand geometry that is near the edge of the target object from the camera's perspective. This creates a circular-shaped "bleed" artifact where hand geoms adjacent to the target geom get included because the re-cast ray hits the target geom at a slightly different angle/position.

## Root Cause Analysis

The filtering pipeline in `mujoco_scene_state_publisher_node.py:420-453` works as follows:

1. **Depth rendering**: MuJoCo renders the full scene (hand + object) into a depth buffer (`mujoco_scene_state_publisher_node.py:347-348`)
2. **Point cloud generation**: All valid depth pixels are back-projected into 3D camera-frame points (`mujoco_scene_state_publisher_node.py:404-418`)
3. **Ray-cast filtering**: For each point, a ray is cast from the camera through the point's direction. If `mj_ray` reports the first hit geom is the target geom, the point is kept (`mujoco_scene_state_publisher_node.py:430-452`)

The bug is in step 3. The ray direction is computed by normalizing the camera-frame 3D point position:

```
ray_cam = point / ||point||    # normalized direction from camera origin through point
```

Then `mj_ray` is called with this direction from `cam_pos`. The problem is that **the 3D point's position is used only to derive a ray direction, but the ray distance is not compared against the point's actual depth**. When a depth pixel was generated by the hand (which is in front of the object from the camera's perspective), the ray from the camera through that pixel's direction may still hit the target geom at a farther distance. Since the filter only checks `geomid[0] == self.target_geom_id` without verifying that the ray intersection distance matches the point's original depth, hand-generated points that happen to have a ray passing through the target geom at some distance are incorrectly kept.

This explains the circular artifact: the hand wraps around the object, and from the camera's viewpoint, the silhouette of the hand against the object creates a ring of pixels where the ray passes through hand geometry first but then continues to hit the target object behind it.

## Implementation Plan

- [ ] **Task 1. Add depth distance check to `filter_points_by_target_geom`**
  In `mujoco_scene_state_publisher_node.py:420-453`, after the `mj_ray` call confirms the hit geom is the target, add a check that the ray intersection distance (`dist`) is approximately equal to the original point's depth (its Z coordinate in MuJoCo camera frame). If the distances differ by more than a small tolerance (e.g., the TSDF resolution or a configurable margin), the point was generated by a different (closer) geometry and should be rejected.
  
  Rationale: This directly addresses the root cause by ensuring that only points whose depth matches the ray-cast distance to the target geom are kept. Points generated by the hand will have a shorter depth than the ray-cast distance to the target, so they will be filtered out.

- [ ] **Task 2. Compute and pass original depth to the filter function**
  Modify `depth_to_camera_points` (or the call site in `on_depth_timer`) to also return or retain the original depth (Z in camera frame) for each point, so it can be compared in `filter_points_by_target_geom`. Currently, the camera-frame Z is already available as `points_cam_ros[:, 2]`, so no structural change is needed — just use it in the comparison.

- [ ] **Task 3. Add a configurable depth tolerance parameter**
  Add a new ROS parameter (e.g., `depth_match_tolerance`) with a sensible default (e.g., `0.01` meters = 1cm, or roughly 2x the TSDF resolution of 5mm) to control how closely the ray-cast distance must match the point depth. This makes the filter tunable without code changes.

## Verification Criteria

- [ ] The segmented point cloud (`/segmented_object_cloud`) no longer contains hand geometry points when the hand is near/around the target object
- [ ] The circular/annular bleed artifact around the object silhouette is eliminated
- [ ] All target object points that were correctly segmented before are still present (no regression in object coverage)
- [ ] The depth tolerance parameter can be adjusted via launch file argument

## Potential Risks and Mitigations

1. **Over-filtering target object points at edges**
   Risk: If the depth tolerance is too tight, points at the silhouette edges of the target object (where the ray grazes the surface) might be rejected because the depth buffer quantization or ray-cast precision differs slightly.
   Mitigation: Use a generous tolerance (1-2cm) and make it configurable. The TSDF resolution is 5mm, so a 1cm tolerance gives 2x margin.

2. **Performance impact of additional comparison**
   Risk: Adding a float comparison per point is negligible, but worth noting.
   Mitigation: This is a trivial O(1) addition per point inside the existing per-point loop — no measurable performance impact.

3. **Depth buffer precision at far range**
   Risk: At larger distances, depth buffer precision decreases, potentially causing false negatives.
   Mitigation: The `max_depth` is 1.5m and the tolerance is in world-space meters, so this should not be an issue at the operating range of the hand.

## Alternative Approaches

1. **Use MuJoCo segmentation rendering instead of ray casting**: MuJoCo supports rendering a segmentation image where each pixel is labeled with the geom ID that generated it. This would completely eliminate the need for per-point ray casting and would be both faster and more accurate. The approach would be: render a seg image, then for each depth pixel, simply check if the seg label matches the target geom ID. This is the "correct" solution but requires more significant changes to the rendering pipeline.

2. **Exclude hand geoms from the depth rendering**: Set `geomgroup` to exclude hand geoms during depth rendering so they never appear in the depth buffer. This would be simpler but means the depth image wouldn't represent the true scene (hand wouldn't occlude the object), which might be undesirable for other consumers of the depth image.

3. **Post-filter using geom bounding volumes**: After the initial ray-cast filter, do a second pass checking each kept point against the bounding volume of the target geom. Points outside the bounding volume would be rejected. This is less precise but simpler.

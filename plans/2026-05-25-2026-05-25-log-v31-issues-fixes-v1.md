# Log v31 Fixes — Wrist Rotation Publish + Twist Deactivation on APPROACHING

## Objective

Fix two critical issues preventing hand/wrist movement in log v31:

1. **Issue 1 (P0)**: The wrist rotation is gated by `publish_initial_commands` in the preshaping bridge, preventing the proximity controller from ever committing a plan.
2. **Issue 4 (P1)**: Twist propagation continues running during APPROACHING, producing spurious segmentation clicks and wasting compute.

## Implementation Plan

### Issue 1: Wrist Rotation Always Published as Planner Topic

**Root Cause**: In `preshaping_service_bridge_node.cpp:530-534`, the wrist rotation publish on `/grasp_preshaping/wrist_pose` is inside the `if (publish_initial_commands_)` guard. When `publish_initial_commands: false` (the real hardware config), the wrist rotation is never published. The proximity controller requires all three plan parts (closures, wrist, hand frame) to commit — without wrist, the plan never commits, and no wrist/finger commands are ever sent.

**Files to modify**:
- `src/grasp_preshaping/nodes/preshaping_service_bridge_node.cpp`

- [ ] **1.1** Move the wrist rotation publish **outside** the `publish_initial_commands_` guard so it always publishes as a planner topic. The wrist rotation is needed by the proximity controller regardless of whether immediate finger commands are sent.

  Current code (lines 528-534):
  ```cpp
  // ── Publish wrist rotation in degrees (immediate) ───────────────────
  // -- Publish wrist rotation in degrees (immediate, if enabled) --
  if (publish_initial_commands_) {
    std_msgs::msg::Float64 wrist_msg;
    wrist_msg.data = ffi_response.wrist_rotation_deg;
    wrist_pose_pub_->publish(wrist_msg);
  }
  ```

  New code:
  ```cpp
  // ── Publish wrist rotation in degrees (always, for proximity controller) ──
  {
    std_msgs::msg::Float64 wrist_msg;
    wrist_msg.data = ffi_response.wrist_rotation_deg;
    wrist_pose_pub_->publish(wrist_msg);
  }
  ```

  **Rationale**: The wrist rotation is a planner output (like target_hand_pose and target_finger_closures) and must always be published. The `publish_initial_commands_` flag should only gate the *immediate* controller commands (finger preshape positions sent directly to joint controllers), not the planner topics consumed by the proximity controller.

- [ ] **1.2** Rebuild the `grasp_preshaping` C++ package inside the container:
  ```
  make build-pkg PKG=grasp_preshaping
  ```
  This is required because the bridge is a C++ node. The previous Pose→PoseStamped fix also needs this rebuild to take effect.

### Issue 4: Deactivate Twist Propagation on APPROACHING Entry

**Root Cause**: The pipeline manager only deactivates twist propagation in two places:
1. On EMG OPEN → RELEASING (`pipeline_manager_node.py:394`)
2. On collision distance < stop threshold (`pipeline_manager_node.py:548-553`)

The collision distance check relies on twist propagation publishing `/twist_propagation/collision_distance`, but after the first hit is detected, twist propagation enters `WAITING_FOR_SEGMENTATION` and stops publishing collision distances. So the stop-distance deactivation never fires during APPROACHING.

Meanwhile, twist propagation returns to IDLE after receiving the segmented cloud (our v30 fix) and immediately starts detecting new hits and publishing new segmentation clicks during APPROACHING — wasting GPU compute and producing spurious segmentations.

**Files to modify**:
- `src/pipeline_manager/pipeline_manager/pipeline_manager_node.py`

- [ ] **4.1** Add twist propagation deactivation in the `_on_preshaping_response` method, right after the successful transition to APPROACHING.

  In `_on_preshaping_response` (line 657-672), after the successful transition to APPROACHING at line 661, call `_deactivate_twist_propagation()`:

  Current code (lines 657-672):
  ```python
  def _on_preshaping_response(self, future):
      try:
          response = future.result()
          if response.success:
              self._transition(State.APPROACHING, f'Preshaping: {response.message[:80]}')
          else:
              ...
      except Exception as e:
          ...
      finally:
          # NOTE: twist is NOT deactivated here during normal flow.
          # The twist is deactivated later by _on_collision_distance when
          # the hand reaches the stop-distance threshold during APPROACHING.
          pass
  ```

  New code:
  ```python
  def _on_preshaping_response(self, future):
      try:
          response = future.result()
          if response.success:
              self._transition(State.APPROACHING, f'Preshaping: {response.message[:80]}')
              self._deactivate_twist_propagation()
          else:
              ...
      except Exception as e:
          ...
  ```

  Remove the `finally` block with the outdated comment since twist is now deactivated immediately on APPROACHING entry.

  **Rationale**: Once preshaping succeeds and the pipeline enters APPROACHING, twist propagation has served its purpose. The proximity controller now drives the hand/wrist based on the committed plan. Keeping twist propagation active produces spurious clicks, triggers unnecessary segmentations, and wastes GPU compute.

- [ ] **4.2** Remove the now-redundant collision-distance-based deactivation in `_on_collision_distance`. Since twist is deactivated on APPROACHING entry, the collision distance check for APPROACHING state will never fire. Simplify the condition to only check TWISTING state:

  Current code (lines 547-553):
  ```python
  if self._state in (State.TWISTING, State.APPROACHING):
      if 0.0 < msg.data < self._twist_stop_distance:
          self._deactivate_twist_propagation()
  ```

  New code:
  ```python
  if self._state == State.TWISTING:
      if 0.0 < msg.data < self._twist_stop_distance:
          self._deactivate_twist_propagation()
  ```

  **Rationale**: Twist propagation is now deactivated when APPROACHING is entered, so the APPROACHING branch in this check is dead code. Keeping only TWISTING makes the intent clear.

## Verification Criteria

- [ ] **VC-1**: After rebuilding and running the pipeline, when preshaping succeeds and the pipeline transitions to APPROACHING, the proximity controller logs `"New plan committed — closures=..., wrist=...°"`. This confirms all three plan parts (closures, wrist, hand frame) are received.
- [ ] **VC-2**: After APPROACHING entry, the proximity controller logs `"Entered near zone"` or `"FAR mode"` messages, confirming the control loop is active and computing distance.
- [ ] **VC-3**: After APPROACHING entry, no further `"Hit found at"` messages appear from twist propagation. The log should show `"Twist propagation deactivated"` right after the APPROACHING transition.
- [ ] **VC-4**: No spurious segmentation clicks or inference runs after APPROACHING entry.

## Potential Risks and Mitigations

1. **Risk: C++ rebuild not applied**
   Mitigation: The plan explicitly calls for `make build-pkg PKG=grasp_preshaping`. Both the PoseStamped fix (from v30) and the wrist publish fix require this rebuild. Without it, neither fix takes effect.

2. **Risk: Twist deactivation too early — hand hasn't reached target yet**
   Mitigation: This is not a concern. Twist propagation's job is to *detect* the target object and trigger segmentation/preshaping. Once preshaping completes, the proximity controller takes over hand guidance. Twist propagation has no role during approach.

3. **Risk: Wrist rotation published even when no proximity controller is running**
   Mitigation: Harmless — the topic just has no subscribers. The wrist rotation is a small Float64 message with no side effects.

## Alternative Approaches

1. **Alternative for Issue 1**: Instead of moving the publish outside the guard, add a separate "planner wrist" topic that always publishes. This would keep the immediate command path clean but adds topic complexity. Rejected — the existing `/grasp_preshaping/wrist_pose` topic is already the planner topic consumed by the proximity controller; the fix is simply to always publish on it.

2. **Alternative for Issue 4**: Add a pipeline state subscription in twist propagation and suppress clicks when state != TWISTING. This would keep twist running but silent. Rejected — deactivation is cleaner (stops all compute, clears state, releases resources).
